## 1. Что эксплуатируем

DzenWriter запускается как один стек Docker Compose на одном хосте:

| Сервис     | Назначение                                                  | Состояние                                   |
| ---------- | ----------------------------------------------------------- | ------------------------------------------- |
| `postgres` | PostgreSQL 16, том `dzenwriter_pgdata`                      | healthcheck `pg_isready`                    |
| `migrate`  | одноразовые миграции перед стартом API                      | завершается с кодом 0                       |
| `api`      | NestJS API, SSE-генерация, доступ к PostgreSQL              | healthcheck `/ready`                        |
| `web`      | статика SPA и внутренний прокси `/api`, `/health`, `/ready` | healthcheck через `wget`                    |
| `Caddy`    | внешний reverse proxy компании: TLS 1.2+, h2 и домен        | вне Docker Compose, инфраструктура компании |

Наружу открывается только Caddy. Он терминирует TLS (1.2+, h2) для домена `dzenwriter.iiruchating.ru` и проксирует запросы на `web` (по умолчанию `127.0.0.1:${WEB_PORT}`). PostgreSQL слушает только loopback. Сертификаты и конфигурация Caddy живут в инфраструктуре компании и в этом репозитории не настраиваются.

Ограничения текущей версии:

- один экземпляр API: отмена генерации хранится в памяти процесса;
- нет встроенного планировщика: бэкапы и очистка сессий запускаются systemd timer на хосте;
- внешний мониторинг — Prometheus + blackbox; healthcheck Docker не заменяет алерты дежурному;
- резервные копии шифруются через `age` и выгружаются в Selectel S3 по стандарту компании.

## 3. Резервные копии и восстановление

### 3.1. Стандарт компании: `pg_dump` → `age` → Selectel S3

Резервная копия готовится на хосте и сразу шифруется:

1. `pg_dump --format=custom` запускается внутри контейнера `postgres`.
2. Поток передаётся в `age` с публичным ключом компании.
3. Зашифрованный файл `dzenwriter-<UTC>.dump.age` выгружается в Selectel S3.
4. Правило lifecycle в бакете удаляет объекты старше 30 дней.

Приватный ключ `age` хранится в менеджере секретов компании, не в репозитории и не в S3. Доступ к бакету — только у Tech lead и дежурного.

Подготовка зашифрованного файла:

```bash
docker compose exec -T postgres pg_dump \
  --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" --format=custom \
  | age -r "$AGE_RECIPIENT" \
  > "/var/backups/dzenwriter/dzenwriter-$(date -u +%Y%m%dT%H%M%SZ).dump.age"
```

Выгрузку в Selectel S3 выполняет штатный S3-клиент компании. Endpoint, бакет и ключи доступа берутся из секретов инфраструктуры.

### 3.2. Расписание и retention

Ежедневный запуск — systemd-таймер `dzenwriter-backup.timer` в 02:30 MSK:

```ini
[Timer]
OnCalendar=*-*-* 02:30:00 Europe/Moscow
Persistent=true
```

Сервис `dzenwriter-backup.service` выполняет пайплайн из раздела 3.1 и выгружает файл в S3. Логи смотрят через `journalctl`.

Проверка, что таймер активен:

```bash
systemctl list-timers dzenwriter-backup.timer
journalctl -u dzenwriter-backup.service --since "24 hours ago"
```

Retention 30 дней задаётся lifecycle-правилом S3, а не локальной ротацией. Локальные файлы можно удалять после успешной выгрузки.

### 3.3. Проверка восстановления на staging

`pnpm db:backup:verify` запускается только на staging. На проде проверку не выполняют: это создаёт нагрузку и не проверяет восстановление на другом хосте.

1. Скачайте последний `.dump.age` из Selectel S3 на staging.
2. Расшифруйте его приватным ключом `age` в файл `.dump`.
3. Запустите проверку в каталоге staging-стека:

```bash
pnpm db:backup:verify /path/to/dzenwriter-2026-11-11T02-30-00-000Z.dump
```

Скрипт создаёт временную базу `dzenwriter_restore_<timestamp>` в PostgreSQL staging, восстанавливает дамп с `--single-transaction`, проверяет обязательные таблицы, наличие миграций и читает счётчики, затем удаляет временную базу. Рабочая база staging не изменяется.

Ежемесячный журнал:

| Месяц   | Дата проверки | Файл | Кто проверял | Результат | Замечания |
| ------- | ------------- | ---- | ------------ | --------- | --------- |
| 2026-11 |               |      |              |           |           |
| 2026-12 |               |      |              |           |           |
| 2027-01 |               |      |              |           |           |

Если проверка не прошла, запуск новых изменений в продакшене приостанавливается до выяснения причины: непроверенная копия не считается резервной.

### 3.4. Аварийное восстановление

Восстановление поверх рабочей базы — destructive-операция. Выполняйте её только при подтверждённом сбое и после создания страховочной копии текущего состояния.

1. Остановить запись:

   ```bash
   docker compose stop api web
   ```

2. Сделать страховочную копию текущей базы по стандарту раздела 3.1:

   ```bash
   docker compose exec -T postgres pg_dump \
     --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" --format=custom \
     | age -r "$AGE_RECIPIENT" \
     > "/var/backups/dzenwriter/dzenwriter-emergency-$(date -u +%Y%m%dT%H%M%SZ).dump.age"
   ```

   Если база повреждена настолько, что `pg_dump` не работает, зафиксируйте это в инциденте и переходите к восстановлению из последней исправной копии.

3. Пересоздать базу (подставьте свои `POSTGRES_USER` и `POSTGRES_DB`):

   ```bash
   docker compose exec -T postgres dropdb --username dzenwriter --force dzenwriter
   docker compose exec -T postgres createdb --username dzenwriter dzenwriter
   ```

4. Расшифровать и восстановить дамп:

   ```bash
   age -d -i /secure/age-identity.txt \
     -o /var/backups/dzenwriter/restore.dump \
     /var/backups/dzenwriter/dzenwriter-2026-11-11T02-30-00-000Z.dump.age

   docker compose exec -T postgres pg_restore \
     --username dzenwriter --dbname dzenwriter \
     --no-owner --no-acl --single-transaction --exit-on-error \
     < /var/backups/dzenwriter/restore.dump
   ```

5. Поднять стек и проверить готовность:

   ```bash
   docker compose up -d --wait
   curl --fail http://127.0.0.1:8080/health
   curl --fail http://127.0.0.1:8080/ready
   ```

6. Проверить вход, доску, карточку материала, версии и последнюю публикацию. Записать время восстановления и точку восстановления (RPO) в журнал инцидента.

Если восстановление не удалось, не повторяйте destructive-команды «наугад»: остановите работы, сохраните логи и обратитесь к Tech lead.

## 4. Очистка сессий

Активная сессия — это запись, у которой `expires_at > now` и `revoked_at IS NULL`. Истёкшие и отозванные сессии не нужны для входа и не используются в аудите, поэтому удаляются.

Скрипт `apps/api/src/scripts/cleanup-sessions.ts` удаляет их одним запросом и печатает число. Он не трогает пользователей, материалы и журнал аудита.

Локально:

```bash
pnpm sessions:cleanup
```

В контейнере (в образе есть скомпилированный скрипт):

```bash
docker compose exec -T api node dist/scripts/cleanup-sessions.js
```

Рекомендуемое расписание — ежедневно в 03:00 по Москве:

```cron
TZ=Europe/Moscow
0 3 * * * cd /srv/dzenwriter && docker compose exec -T api node dist/scripts/cleanup-sessions.js >> /var/log/dzenwriter-sessions.log 2>&1
```

Проверка:

```bash
tail -n 5 /var/log/dzenwriter-sessions.log
# Ожидаемая строка: «Удалено сессий: N», N может быть 0
```

Очистка не является срочной: истёкшая сессия и так не проходит проверку входа, а отозванная — тоже. Задача гигиены — не давать таблице расти бесконечно. Если API остановлен, очистку можно пропустить и выполнить после запуска.

## 4.1. Перепроверка членства в организации (P1-13)

Раз в сутки скрипт `membership:recheck` спрашивает GitHub про каждого, у кого активная сессия и был реальный вход через GitHub: участник организации — ок; не участник — отключение с отзывом всех сессий и записью «Выведен из организации» в журнале. Токен берётся из `GITHUB_ORG_TOKEN` (`read:org`, ротация 90 дней); без токена скрипт выходит с пометкой «не активна». Подробности — ADR-0005.

Локально:

```bash
pnpm --filter @dzenwriter/api membership:recheck
```

В контейнере (токен передаётся окружением):

```bash
docker compose exec -T api node dist/scripts/membership-recheck.js
```

Скрипт лежит в `apps/api/src/scripts` и попадает в `dist/scripts/membership-recheck.js`; `GITHUB_ORG_TOKEN` передаётся в сервис `api` через `docker-compose.yml`.

Рекомендуемое расписание — ежедневно в 04:00 MSK (`Europe/Moscow`):

```cron
TZ=Europe/Moscow
0 4 * * * cd /srv/dzenwriter && docker compose exec -T api node dist/scripts/membership-recheck.js >> /var/log/dzenwriter-membership.log 2>&1
```

Проверка:

```bash
tail -n 5 /var/log/dzenwriter-membership.log
# Ожидаемая строка: «Перепроверка: проверено N, отключено K, пропущено M»
```

Если в строке есть «ТОКЕН НЕВАЛИДЕН» — перепроверка остановилась на первом отказе GitHub (401/403): продлить или заменить `GITHUB_ORG_TOKEN`, затем запустить повторно. Пользователей в этот день не отключают — токен не является вердиктом об организации.

## 5. Runbook: сбой LLM

### 5.1. Как понять, что случилось

Симптомы у автора: запуск генерации завершается ошибкой, версия не создаётся, в карточке материала виден текст ошибки. Статус запуска и код ошибки хранятся в `generation_runs`.

```bash
docker compose exec -T postgres psql \
  --username dzenwriter --dbname dzenwriter \
  --command "SELECT created_at, status, error_code, provider, model, latency_ms
             FROM generation_runs
             WHERE status = 'failed'
             ORDER BY created_at DESC
             LIMIT 20;"
```

| `error_code`       | Что означает                                     | Что делать в первую очередь                                     |
| ------------------ | ------------------------------------------------ | --------------------------------------------------------------- |
| `unavailable`      | провайдер недоступен, 5xx или его лимит запросов | проверить статус провайдера, сеть и egress; повторить позже     |
| `timeout`          | провайдер не ответил за `LLM_TIMEOUT_MS`         | проверить провайдера; при стабильной деградации поднять таймаут |
| `auth`             | провайдер отклонил ключ (401/403)                | проверить срок действия ключа, ротировать ключ                  |
| `invalid_response` | ответ не JSON, без текста или не прошёл схему    | проверить модель и совместимость; схема/промпт не менялись?     |
| `aborted`          | запуск отменён человеком, это не сбой            | действий не требуется                                           |

Локальный отказ до обращения к провайдеру (429) означает исчерпанный дневной лимит запусков или бюджет. Это не `generation_runs`: запуск ещё не создан. Текст отказа: «Дневной лимит генераций исчерпан…» или «Дневной бюджет генерации исчерпан…».

### 5.2. Общая диагностика

1. Убедиться, что приложение и база живы:

   ```bash
   curl -fsS http://127.0.0.1:8080/health
   curl -fsS http://127.0.0.1:8080/ready
   ```

2. Проверить настройки без вывода секрета:

   ```bash
   docker compose exec -T api node -e \
     "console.log({provider:process.env.LLM_PROVIDER,baseUrl:process.env.LLM_BASE_URL,model:process.env.LLM_MODEL,timeoutMs:process.env.LLM_TIMEOUT_MS})"
   ```

3. Проверить страницу статуса провайдера и доступность его API с хоста. Не отправляйте в чат и тикеты ключ и тексты статей. Быстрая проверка ключа и структурированного ответа — `pnpm --filter @dzenwriter/api llm:probe` (без вывода ключа).
4. Посмотреть последние ошибки API:

   ```bash
   docker compose logs --since=30m api | tail -n 100
   ```

5. Не менять `.env` «на лету» в контейнере: изменения применяются пересозданием API.

### 5.3. Провайдер недоступен или отвечает 5xx

1. Если сбой короткий, подождите 5–15 минут и повторите генерацию. Приложение делает один повтор только при ошибке схемы ответа, сетевые ошибки автоматически не повторяются.
2. Если провайдер недоступен дольше 30 минут, сообщите команде: генерация временно недоступна, факты, редактор и ревью работают.
3. При длительном сбое Tech lead может переключить API на резервный OpenAI-совместимый endpoint:
   - изменить `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` в `.env` на хосте;
   - пересоздать API: `docker compose up -d --force-recreate api`;
   - проверить генерацию на тестовом материале.
4. Не включайте `LLM_PROVIDER=mock` в продакшене: заглушка создаст версию с фиктивным текстом, которую можно принять за настоящую. При `NODE_ENV=production` и `LLM_PROVIDER=mock` старт API и `config:validate` завершаются ошибкой конфигурации (P0-4).
5. После восстановления проверьте, что новый запуск имеет статус `succeeded`, и сообщите команде.

### 5.4. Исчерпан лимит или бюджет

Различайте два случая.

**Наш суточный лимит.** Приложение отвечает 429 до создания запуска. Проверьте значения:

```bash
docker compose exec -T api node -e \
  "console.log({runsPerUser:process.env.LLM_DAILY_LIMIT_PER_USER,budgetUsd:process.env.LLM_DAILY_BUDGET_USD})"
```

Посмотрите расход за московские сутки:

```bash
docker compose exec -T postgres psql \
  --username dzenwriter --dbname dzenwriter \
  --command "SELECT count(*) AS runs, coalesce(sum(cost_usd), 0) AS cost_usd
             FROM generation_runs
             WHERE created_at >= date_trunc('day', now() AT TIME ZONE 'Europe/Moscow') AT TIME ZONE 'Europe/Moscow';"
```

Решение об увеличении лимита принимает владелец бюджета. Изменение `.env` требует пересоздания API:

```bash
docker compose up -d --force-recreate api
```

**Лимит провайдера.** Провайдер отвечает 429; приложение записывает запуск как `unavailable`. Проверьте квоту в панели провайдера. Варианты: дождаться сброса квоты, перейти на другой тариф или временно переключиться на резервный endpoint. Не обходите лимит созданием нескольких ключей без согласования.

### 5.5. Ключ недействителен

Признак: `error_code = auth`, автор видит «Провайдер отклонил ключ».

1. Проверьте в панели провайдера, не отозван ли ключ и не истёк ли срок.
2. Выпустите новый ключ с минимальными правами.
3. Замените `LLM_API_KEY` в `.env` на хосте. Не пишите ключ в git, чат, тикеты и логи.
4. Пересоздайте API и проверьте генерацию:

   ```bash
   docker compose up -d --force-recreate api
   docker compose exec -T api node -e "console.log(process.env.LLM_PROVIDER, process.env.LLM_MODEL)"
   ```

5. Убедитесь, что новый запуск завершился успешно. Старый ключ отзовите, если он ещё действует.

### 5.6. Подозрение на утечку ключа

1. Немедленно отзовите ключ у провайдера и выпустите новый.
2. Замените ключ на сервере способом из раздела 5.5. Не сохраняйте старый ключ в истории команд.
3. Проверьте журнал аудита и счета провайдера на подозрительные запуски и расход.
4. Сообщите Tech lead и владельцу продукта; заведите инцидент без секретов и текстов статей.
5. После стабилизации выясните источник утечки: история shell, CI-переменные, скриншоты, переписка. Удалите ключ отовсюду, где он мог сохраниться.

### 5.7. Модель стабильно возвращает неверный формат

Если в журнале много `invalid_response`, а провайдер доступен:

1. Проверьте, какая модель указана в `LLM_MODEL`, и поддерживает ли она structured output с JSON-схемой.
2. Не меняйте схему ответа и промпт в спешке: это изменит поведение всех стилей. Сначала соберите 2–3 примера кодов ошибок без текстов статей.
3. Если проблема началась после смены модели, верните предыдущую модель через `.env` и пересоздайте API.
4. Если проблема воспроизводится на прежней модели, передайте Tech lead примеры и код ошибки; до исправления авторы могут работать в редакторе вручную.

### 5.8. Завершение инцидента

- Генерация на тестовом материале завершилась со статусом `succeeded`.
- Авторы уведомлены, что можно продолжать работу.
- В журнале инцидента записаны: время начала и конца, сценарий, затронутые запуски, действие, кто выполнял, что изменили.
- Если меняли ключ, лимит или endpoint, запись добавлена в журнал изменений конфигурации (без секретов).
- Если инцидент повторился дважды за месяц, создаётся задача на устранение причины, а не только на ручное восстановление.

### 6.1. Быстрый деплой

Первичный деплой и повторное обновление на сервере запускаются из корня репозитория:

```bash
./scripts/deploy.sh
```

Скрипт идемпотентен, поэтому его можно запускать повторно. Он:

1. проверяет наличие `.env`, Docker, Docker Compose и `curl`;
2. проверяет, что `POSTGRES_PASSWORD` задан и не равен `dzenwriter`;
3. выводит текущую ветку и короткий хеш git-коммита;
4. загружает образы из GHCR через `docker compose pull`;
5. применяет миграции одноразовым сервисом `docker compose run --rm migrate`;
6. поднимает стек через `docker compose up -d --wait`;
7. до 60 секунд проверяет `http://127.0.0.1:${WEB_PORT}/health` и `/ready`;
8. при ошибке печатает `docker compose logs api` и завершается с ненулевым кодом;
9. в конце выводит внутренний адрес приложения; публичный — `https://dzenwriter.iiruchating.ru`.

`WEB_PORT` берётся из `.env` (по умолчанию `8080`). Если переменная задана в окружении, приоритет у неё — как и у `docker compose`.

**Скрипт не делает резервную копию базы.** Бэкапы — отдельный systemd-таймер (раздел 3.2). Перед обновлением с рискованной миграцией сделайте копию вручную и согласуйте план отката.

### 6.2. Обновление приложения

1. CI публикует образы `api` и `web` в GHCR с тегами `latest` и `sha-<commit>`.
2. Сделать резервную копию по стандарту раздела 3.1.
3. Обновить код и выполнить `./scripts/deploy.sh`: скрипт скачает образы, применит миграции и перезапустит стек.
4. Проверить `https://dzenwriter.iiruchating.ru/health`, `/ready`, вход и одну генерацию.
5. При ошибке вернуть предыдущий `sha-<commit>` или digest через `API_IMAGE`/`WEB_IMAGE` в `.env` и снова выполнить `./scripts/deploy.sh`.

Откат миграций не автоматизирован: схема меняется только вперёд. Перед рискованной миграцией делается отдельная резервная копия и согласуется план отката.
